# Does an agent fix an update's breaks better with DepTime? Results (DT-QA-27)

Protocol: `README.md` here. Probe environments that didn't install: none.

## What it says (written after scoring; the tables below are `score.py`'s)

**The bar is met on all three lines.** On 60 broken updates that neither DepTime nor its command had ever been run
on, Claude Code on Sonnet 5.5 left the code working in 52 sessions with `/deptime:fix-upgrade` at 0.2.3 (arm B, 86.7%)
and in 46 alone (arm A, 76.7%). B had one session whose fix broke something new, A three. B fixed 96.0% of the 373
confirmed breaks, A 89.3%. Paired by task, B fixed 8 that A didn't and A 2 that B didn't (McNemar's exact p = 0.109),
so the 10-point gap in sessions is suggestive, not proven, at this size; the bar asks only that B match A. B did it at
about half the cost: median 16 turns against 25, 0.6 minutes against 1.2, 3,932 output tokens against 6,569, and
1,572 changed lines nobody asked for against A's 4,293.

**DT-QA-26's loss causes, read by hand as README.md asks.** QA-26's B left breaks DepTime listed with no replacement
(3 of its 4 losses). Here DepTime listed 267 of the 373 confirmed breaks with no replacement (the set is mostly
removals across major versions: langchain 1.x, mistralai 3.x, mcp 2.x). B fixed 253 of them (94.8%; 7 removed, 6
still broken, 1 can't tell), A 239 (89.5%). Of the breaks listed with a replacement, B fixed 99 of 99, A 87. B left
lines in place only on llama-index-core's removed low-level agent API (`AgentRunner`, `Task`, `TaskStepOutput`, two
tasks), which A didn't fix either. QA-26's other cause, streamlit's top-level calls (DT-DATA-83), had one task here,
and both arms fixed it.

**Why B lost the 2 tasks only A fixed** (README.md asks which part: DepTime's answer, the command's instructions, the
shell or the agent):

- **1: DepTime's answer.** crewai 0.1.32 → 1.15.41: `Task(agent=, description=)` now needs `expected_output`, a
  pydantic field with no default. `check-upgrade` reported no break: DepTime doesn't check a pydantic model's required
  fields (its `__init__` takes `**data`). B, with a clean report, changed nothing; A added the field. One case, so per
  the holdout miss rule it is held until it recurs.
- **1: the command's instructions and the scoring rule together.** On langchain 0.0.x → 1.5.0 (`nrcrews`), B fixed all
  19 confirmed breaks, but the project's own `Language.cpp` (no such member at the old version either: the set labels
  it `excluded`, "doesn't work in from") moved with B's import change to `langchain_text_splitters.Language.cpp`, which
  the scoring counts as a new use that breaks. B left it, as step 4 says for uses broken at the old version too; A
  rewrote it to `Language.CPP`. Scored as the protocol says; the verdict doesn't depend on it.

None came from a wrong answer of DepTime's. B's 8 wins: on each, A left breaks in place, deleted the code that used
them, or wrote a fix the scoring couldn't confirm (mcp 2.x 11 of 11, three langchain tasks, mistralai 3.x, transformers
5.x, langchain-community, pydantic-ai-slim), and on three of them (langchain, langchain-community, pydantic-ai-slim)
A's fix broke something new.

**The shell.** 42 of B's 60 sessions had a Bash command denied (QA-26: 35 of 66). Nearly all were the agent trying to
install or download the new release to read it (`mkdir` + `uv venv`, `uvx --from`, `pip download`, `curl`, `gh api`)
or to edit with `sed` or a Python script; one was the DepTime command with `cd ... &&` in front. Each agent went on with
the file and web tools; none of the denials stopped a session. A had no shell.

**Scoring:** no change to `score.py` after the first scored pass. No session ended on a service error and none timed out.

**Hand checks:** 262 uses (261 work, 1 breaks: `langchain_text_splitters.Language.cpp`) and 10 breaks (all fixed),
each with the released source file and line, in `hand-checks.json`. They were settled blind to arm, before the first
score was read: the uses from the blinded `hand-todo.json` alone (221 of them are langchain 1.5.0 sessions' uses of
the split-out packages, `langchain_classic`, `langchain_community`, `langchain_text_splitters`, `langchain_openai` and
others, which the probe's langchain environment doesn't install), then the 10 breaks from each session's diff,
printed by check id without the arm or run. A static reader of the unpacked wheels did the first pass; every use it
couldn't settle, every call it judged only through a `**kwargs` passthrough and every break it reported was read by
hand.

**What it means for DepTime.** The bar is met, so per README.md DT-OSS-17 freezes the hand-off (the command and the
report's "For a coding agent" block) as it is at 0.2.3. Against QA-26 on different tasks: B went from 72.7% to 86.7%
and A from 69.7% to 76.7%. This set's updates were easier for both arms. B's share of the gap grew (3 points to 10),
which is what the two fixes (DT-GTM-09, DT-DATA-83) were meant to do.

**Limits.** 60 small projects with no tests the agent could run, scored by running each use rather than the project;
one model; one run per arm, so a task's two sessions differ by chance as well as by arm; tasks weighted toward
langchain (10), mistralai (7) and mcp (7), with 20 packages in all. Claude Code was 2.1.326 here and 2.1.325 in
QA-26. The paired difference is not significant at this size; the bar was set to ask only that B match A, and it did.
