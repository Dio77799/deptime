# Does an agent fix an update's breaks better with DepTime? Results (DT-QA-05)

Protocol: `README.md` here. Probe environments that didn't install: none.

## What it says (written after scoring; the tables below are `score.py`'s)

**The bar is missed, and not narrowly.** Claude Code on Sonnet 5.5 left the code working in 40 of 50 sessions alone
(arm A, 80%) and 32 of 50 with `/deptime:fix-upgrade` (arm B, 64%). Paired by task and run, B never fixed a task A
missed and A fixed 8 that B missed (McNemar's exact p = 0.008). No arm's fix broke anything new. B was much cheaper and
tidier: median 9 turns against 23, 0.4 minutes against 1.2, a third of the output tokens, and 216 changed lines
nobody asked for against 2,191. With the plugin installed and not named (arm C), the agent called DepTime's MCP tools
in all 25 sessions and fixed 20 (80%, A's rate) with 739 unasked lines in half as many sessions as A.

**Why B lost** (README.md asks which part failed: DepTime's answer, the command's instructions, or the agent). Of the
8 sessions only A fixed:

- **4: the command's instructions on DepTime's `unknown` answers.** On fastmcp 2.10 → 4.1.8 DepTime answered
  `unknown` for `fastmcp.prompts.prompt.PromptMessage` and `TextContent` (names fastmcp re-exports from mcp), and on
  one mcp 2.3.0 task for `types.ClientRequest.model_construct` (DT-CORE-73). The command says `unknown` notices
  "aren't caused by this update" and to leave them alone, so B changed nothing there. That sentence is wrong: `unknown`
  means DepTime can't tell.
- **2: an unread pin and the command's stop rule.** synthtot pins langchain in `setup-requirements.txt`, which
  `check-upgrade` doesn't read; it exited 2 ("pass --from"), and the command says to stop on exit 2. B1 stopped; B2
  passed `--from` and then hit the next cause.
- **2 (and the 0-of-30 and 0-of-17 sessions on the two largest tasks, which A also failed): the report is too big to
  read.** On tasks with many breaks the JSON report ran past the shell's output limit (about 20,000 characters), the
  agent tried to save it to a file or pipe it, and the sandbox denied that (only `uvx deptime==0.2.1 check-upgrade`
  itself is allowed). B then stopped with nothing or part fixed. `check-upgrade --output FILE` exists; the command
  never mentions it.

**The sandbox is part of this result.** `--permission-mode dontAsk` denies every Bash command but the check itself,
and B's agent piped or redirected the check in 44 of 50 sessions. A person running the plugin would be asked, or
would have allowed it. So B measures the hand-off under a stricter shell than a person's, and the trial showed this
once (a denied compound command, two breaks left) without the protocol changing. The `unknown` and stop-rule
failures don't depend on the sandbox.

**What it means for DepTime.** No wrong answer of DepTime's lost B a session: its 8 B-only misses came from breaks
DepTime answered `unknown`, a pin it couldn't read, and a report the agent couldn't read in full. (Five tasks, among
them the two largest, no arm fixed in any session.) The hand-off lost them: it tells the agent to trust DepTime over its own reading, including
where DepTime says it doesn't know, and it hands over a report too large for the agent's shell. Sonnet alone already
fixes most of these updates; DepTime as an optional tool (arm C) kept that success rate at lower cost, and the strict
"fix exactly what it reports" command lowered it. Per README.md, DT-OSS-17 waits and the hand-off is reworked first.

**Scoring corrections made after the first scored pass, before this summary** (all in `score.py`, each making it do
what README.md says; the first pass read A 46%, B 60%, C 56%):

1. a use of another package (`langchain_openai.ChatOpenAI`, `langchain_ollama`, `langchain_qdrant`) failed in the
   probe only because its environment installs just the task's package; README.md makes that `can't tell`, settled
   from that package's released source, not `breaks`;
2. a call the probe finds doesn't bind is a break only once the source confirms it, as the holdout's labels require
   (mcp 2.3.0's `ToolAnnotations(destructive_hint=...)` binds: its models populate by name);
3. the project's own module next to a script (`demo.py`) was read as a library;
4. Poetry pins (`httpx = "^0.28.1"`, `fastmcp = "==4.1.8"`) were read as pinning away from `to`.

They moved A by 34 points, C by 24 and B by 4, against the arm the bar favours. **Hand checks:** 20 uses and 20
breaks, all settled as working or fixed, each with the source file and line (`hand-checks.json`). The last 7 (one
task) were not blind: to read a truncated replacement, the maintainer's agent opened that task's diffs by session
label. Each is a fact about mcp 2.3.0's API that every session of the task wrote the same way.

**Limits.** 25 small projects (most under 15 GitHub stars) with no tests the agent could run; one model; two runs
per arm. "Fixed" means the new code resolves and binds at `to`, not that the program behaves as before. A session that
fetched its own repository: 1 (A1, chromadb, not fixed).
